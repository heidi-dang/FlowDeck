# FlowDeck v2.2.7

FlowDeck v2.2.7 introduces the **Autonomous Developer & User Approval Authorization Model** for Heidi, eliminating false-positive mutation blocks on legitimate local developer workflows while introducing explicit, one-shot user approval workflows for sensitive, external, privileged, or destructive operations.

## Overview & Background

Prior to v2.2.7, FlowDeck applied a strict binary read-only model to the primary orchestrator session. While this prevented unintended filesystem mutations in coordinator mode, it prevented Heidi from acting as an autonomous workspace developer—blocking safe nested command substitutions (e.g. `audit_id="heidi-...-$(date +%Y%m%d-%H%M%S)"` and `sha=$(git rev-parse HEAD)`), local git commits, and temporary directory management.

FlowDeck v2.2.7 re-architects the authorization model with capability tiers (`ALLOW`, `APPROVAL_REQUIRED`, `DENY_INVALID`), scoped one-shot approvals, and a robust anti-flood state machine.

## Key Architecture & Features in v2.2.7

### 1. Three-Tier Capability Authorization Model
- **`ALLOW` (Autonomous Workspace Development)**:
  - Heidi operates directly and autonomously inside the active workspace and temporary roots (`/tmp/`, `/var/folders/`, `$TMPDIR`).
  - Permitted actions: file creation, editing, patching, and deletion within project bounds; local git operations (`git add`, `git commit`, `git checkout`, `git branch`, `git stash`); build, test, and lint runners (`npm`, `bun`, `cargo`, `pnpm`); directory creation and output redirects.
  - Safe nested command substitutions (`$(date ...)`, `$(git rev-parse HEAD)`) are parsed and admitted in context.
- **`APPROVAL_REQUIRED` (Trust-Boundary Operations)**:
  - Operations that cross security, external, or irreversible trust boundaries require explicit user approval via Web UI or CLI.
  - Guarded actions: `git push` and `git push --force`, `npm publish` / `cargo publish` / `twine`, `gh release create`, `sudo` / `su` / system administration, sensitive credential access (`.env`, `~/.ssh`, `*.pem`, `*.key`), external destructive deletions (`rm -rf /...`), cloud and infrastructure deployments (`terraform`, `kubectl`, `pulumi`).
- **`DENY_INVALID`**:
  - Technically malformed, impossible, or unsupported commands are rejected immediately with clear error diagnostics.

### 2. Scoped One-Shot Approval Registry (`src/services/approval-service.ts`)
- **Action Fingerprinting**: Exact fingerprinting incorporating session ID, normalized tool arguments, and working directory.
- **One-Shot Execution**: Approvals transition from `pending` -> `approved` -> `consumed` upon execution. Once consumed, the one-shot token cannot be replayed.
- **Anti-Flood & `WAITING_FOR_APPROVAL` State Machine**: Prevents repeated token-churning retry loops, repetitive guard sound alarms, and UI card flooding.
- **Expiration & Session Isolation**: Approvals feature configurable TTL expiration and strict session boundaries, cleaned automatically upon session termination.

### 3. Nested Substitution & Compound Pipeline Evaluation
- **Recursive Substitution Parsing**: `evaluateShellAuthorization` extracts `$()` and backtick subcommands, ensuring nested dangerous commands (e.g., `$(git push ...)`) escalate approval requirements.
- **Pipeline Risk Inheritance**: Compound commands (`&&`, `||`, `;`, `|`) evaluate all segments and inherit the highest risk level across the pipeline.

### 4. Audit & Governance Logging
- Emits structured events (`approval.required`, `approval.granted`, `approval.denied`, `approval.consumed`) directly to `.codebase/AUDIT.jsonl`.
