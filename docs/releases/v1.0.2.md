# FlowDeck v1.0.2 — Release Integrity

A deterministic and production-gated release pipeline for the FlowDeck Orchestration Engine.

## What's Fixed

### Tag-triggered publish workflow build-order repair

The v1.0.1 publish workflow (`publish.yml`) ran `npm test` **before** `npm run build`. On a fresh tag checkout no `dist/index.js` exists, so the packed-doctor tests (`tests/doctor-packed.test.ts`, `copyDist`) hard-failed and the v1.0.1 tag never published to npm. The publish workflow now builds before running tests, matching the ordering that `ci.yml` already enforced.

### Why PR checks did not catch the v1.0.1 tag workflow defect

`ci.yml` (the pull-request gate) runs `npm run build` before `npm test`, so every PR including the v1.0.1 release PR passed its checks. The publish workflow was never exercised by PR checks: it is triggered only by a `v*` tag push, and the v1.0.1 tag push was the first time the publish ordering ran in anger. The defect was a workflow-ordering divergence between the two files, invisible to PR CI.

## Build-before-test enforcement

- The publish workflow now runs: `npm ci` → `npm run typecheck` → tag/version alignment → `npm run build` → `npm test` → package validation → `npm publish`.
- `tests/publish-workflow-order.test.ts` now locks this ordering with 11 regression invariants and fails against the old v1.0.1 workflow.

## Release-workflow regression coverage

`tests/publish-workflow-order.test.ts` asserts:

1. Install dependencies precedes build.
2. Typecheck precedes publish.
3. Build precedes tests.
4. Tests precede publish.
5. Package validation precedes publish.
6. Bun is pinned to 1.3.14.
7. Tag/package version alignment exists.
8. Registry version-availability validation exists.
9. npm provenance remains enabled.
10. Publish runs only for version tags.
11. No `|| true` masks release failures.

## Bun 1.3.14 pin

`oven-sh/setup-bun@v2` now pins `bun-version: "1.3.14"`. The tag-triggered publish runs on a fresh checkout, so a floating Bun version could change test behaviour between releases.

## Tag/package version alignment

The publish workflow compares `GITHUB_REF_NAME` (the git tag, e.g. `v1.0.2`) against `package.json` version (`1.0.2`) and fails when they differ. A `v1.0.2` tag can never publish a mismatched package version.

## Registry availability check

Before `npm publish`, the workflow verifies the target version is not already present on the registry. Registry lookup failures fail the workflow — they are not hidden — so a duplicate-version publish attempt is impossible.

## npm provenance preservation

`npm publish --provenance --access public` is preserved, backed by the least-privilege `permissions: contents: read, id-token: write`. No broader permissions were added.

## Compatibility

**No runtime configuration migration is required.** This release contains no user-facing runtime changes — it is a release-pipeline integrity release. The runtime package remains functionally identical to v1.0.1 (which is not deprecated; its runtime package is functional).

## Immutability

v1.0.0 and v1.0.1 remain immutable: their tags, npm packages, GitHub releases, and documentation are untouched.
