# FlowDeck v2.0.0 Stable Promotion Design

Date: 2026-08-15

## Goal

Promote the already-proven FlowDeck v2.0.0-rc.1 runtime to the official stable `v2.0.0` release so normal users installing `@heidi-dang/flowdeck` receive FlowDeck v2 through npm `latest`.

The stable release must be functionally identical to the validated RC.1 runtime. No new runtime behavior, Heidi features, orchestration behavior, persistence semantics, FDX behavior, installer behavior, or compatibility changes are permitted in this promotion.

## Starting Point

Stable promotion starts from the current `main` commit:

`32513a722734999d814176f8d4aef66e606a9ce3`

That commit is the merged RC.1 source and is already published immutably as:

- Git tag: `v2.0.0-rc.1`
- npm package: `@heidi-dang/flowdeck@2.0.0-rc.1`
- npm dist-tag: `next`

RC.1 passed the complete release gates and published-artifact runtime smoke, including local OpenCode/Heidi execution, native FDX execution, memory, learning review, `/fd-agents`, real parallel specialist overlap, restart durability, and environment cleanup.

The RC.1 tag, GitHub prerelease, and npm artifact must remain unchanged.

## Stable Promotion Scope

Create `release/v2.0.0` from the current `main` lineage and make only stable-release metadata/documentation changes required to publish `2.0.0`.

Required changes:

1. Change `package.json` version from `2.0.0-rc.1` to `2.0.0`.
2. Change the root package version in `package-lock.json` to `2.0.0` and keep lock metadata internally consistent.
3. Update README release-facing metadata from RC.1 to stable v2.0.0.
4. Change normal installation/upgrade guidance from the prerelease `@next` channel to the stable package/default `latest` channel.
5. Add `docs/releases/v2.0.0.md` as the official stable release notes.
6. Preserve `docs/releases/v2.0.0-rc.1.md` unchanged as historical release-candidate documentation.

No product/runtime source code changes are in scope.

## Stable User Experience

After publication:

- `npm install -g @heidi-dang/flowdeck` installs `2.0.0`.
- `npm install -g @heidi-dang/flowdeck@latest` installs `2.0.0`.
- `npm view @heidi-dang/flowdeck@latest version` returns `2.0.0`.
- `@next` may continue to reference RC.1 unless intentionally changed by a later prerelease; stable promotion does not need to rewrite historical prerelease channel state.
- Existing v1.x users can upgrade through the normal stable install/repair flow.
- RC.1 users can upgrade to `2.0.0` through the same stable install/repair flow.

The README should present v2.0.0 as the current stable release and must no longer direct ordinary users to `@next`.

## Release Notes

`docs/releases/v2.0.0.md` should describe v2.0.0 as the stable release of the runtime proven in RC.1. It should summarize the major v2 capabilities already present, including:

- Heidi persistent USER/AGENT/REPO memory
- cross-session recall
- evidence-backed learning review and versioned learned skills
- governed tool pipelines
- durable scheduling
- adaptive parallel specialist execution
- restart recovery
- native FDX with TypeScript fallback
- hardened installer/duplicate-registration repair
- runtime identity and Doctor verification

The stable notes must not claim new functionality beyond RC.1.

Compatibility remains:

- Node.js `>=20.0.0`
- OpenCode `>=1.4.0`
- FDX compatibility `^0.1.0`

Stable installation guidance should use `@heidi-dang/flowdeck` or `@latest`, followed by the canonical `flowdeck clean-install` / repair and `flowdeck doctor` workflow.

## Verification Design

Before the stable-release PR is merged, verify that the diff from RC.1 contains only approved stable-release metadata/docs changes. Any runtime/source-code delta requires stopping the promotion and treating it as a new release candidate.

Run the complete repository release gates on the stable-release branch, including build, lint, typecheck, skills/docs/schema validation, persistence, orchestration, main tests, FDX parity, v2 milestone/completion checks, parallel benchmark, gatekeeper, isolated clean install, offline installation, release alignment, `verify:full`, and `npm pack` inspection.

The stable release is eligible to merge only with zero unexplained failures.

After merge, rerun release-critical verification against the exact merged `main` commit before tagging.

## Publication Design

The existing tag-triggered publish workflow remains authoritative. It validates tag/package alignment, builds, tests, validates package contents, checks registry availability, derives the release channel, and publishes with npm provenance.

For version `2.0.0`, `scripts/release-channel.mjs` resolves the dist-tag to `latest`.

Publication sequence:

1. Merge the stable-release PR into `main` after all checks are green.
2. Record the exact merged-main SHA.
3. Revalidate that exact commit.
4. Create annotated tag `v2.0.0` on that exact commit.
5. Push only that tag.
6. Allow `.github/workflows/publish.yml` to publish `@heidi-dang/flowdeck@2.0.0` under `latest`.
7. Verify the npm registry reports exact `2.0.0` and `latest = 2.0.0`.
8. Create the GitHub `FlowDeck v2.0.0` release as a normal stable release, not a prerelease.

Never move or overwrite `v2.0.0-rc.1`, and never republish an existing npm version.

## Published Stable Smoke

After npm publication, validate the real registry artifact in an isolated local environment, not the repository checkout or a local tarball.

Required smoke:

- install `@heidi-dang/flowdeck@2.0.0` from npm
- package Doctor passes
- local OpenCode loads exactly one FlowDeck instance
- runtime identity reports `2.0.0`
- Heidi completes a normal task using `heidi / heidi-antigravity`
- native FDX executes successfully on supported local Linux x64
- memory write/read succeeds
- learning review runs with no unexpected `PERSISTENCE_FAILED`
- `/fd-agents` works
- controlled independent specialists show real overlap with maximum concurrency at least 2
- full isolated OpenCode process restart preserves durable state and does not create duplicate registration or duplicate learning

No VMware, external VM, or remote sandbox may be used for runtime acceptance.

## Environment Safety

Before any OpenCode or installation smoke, capture the current local machine state. Testing must use isolated HOME/XDG/npm/OpenCode state wherever possible.

After testing:

- stop all test OpenCode processes
- remove all temporary HOME/XDG/npm/workspace/SQLite/test-registration state
- restore the user's original OpenCode/FlowDeck configuration and global package state
- if OpenCode was not running before the test, leave it not running
- if an existing process had to be stopped, restore the same effective operating mode, command, working directory, and port

Do not expose credentials or secret environment values in logs or release reports.

## Failure Policy

If stable-promotion metadata changes expose a real defect or any runtime/source-code fix is required, do not publish `2.0.0` from that state.

Instead:

1. stop the stable promotion,
2. fix through normal review,
3. issue a new prerelease such as `2.0.0-rc.2`,
4. repeat the required RC validation,
5. return to stable promotion only after the new RC is healthy.

The already-published RC.1 tag and package remain immutable in all cases.

## Acceptance Criteria

The stable release is complete only when all of the following are true:

- stable-release diff contains no functional runtime change
- package and lockfile version are exactly `2.0.0`
- README identifies v2.0.0 as stable and points ordinary installs to stable/latest
- stable release notes exist and accurately describe the proven v2 runtime
- full release verification passes before merge
- stable PR merges into `main`
- exact merged-main commit passes final release verification
- `v2.0.0` tag points to that exact merged-main commit
- canonical publish workflow succeeds
- `@heidi-dang/flowdeck@2.0.0` exists on npm
- npm `latest` resolves to `2.0.0`
- GitHub release is a non-prerelease stable release
- actual published artifact passes isolated local OpenCode/Heidi smoke
- all temporary test state is removed
- the user's pre-test machine state is restored
- working tree is clean
- no remaining P0 or P1 release blocker exists

## Non-Goals

This promotion does not include:

- new Heidi features
- new specialist agents
- new commands
- schema changes
- new FDX behavior
- scheduler changes
- installer redesign
- OpenCode compatibility expansion
- branch-protection/governance redesign
- stable `2.0.1` work

Any such change belongs after v2.0.0 or in a new prerelease if discovered as a blocker.
