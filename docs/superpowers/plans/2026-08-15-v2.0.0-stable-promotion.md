# FlowDeck v2.0.0 Stable Promotion Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Promote the proven `v2.0.0-rc.1` runtime to the official stable `v2.0.0` release so normal npm installs resolve FlowDeck v2 through `latest`, without introducing any new runtime behavior.

**Architecture:** Treat stable release as a promotion of the already-validated RC.1 source, not as a feature release. Start a clean `release/v2.0.0` branch from current `main`, change only version/release documentation metadata, prove the branch has no runtime delta from RC.1, merge through a green PR, tag the exact merged-main commit, let the existing tag-triggered publish workflow publish `2.0.0` to `latest`, then smoke-test the actual npm artifact in an isolated local OpenCode environment and restore the machine exactly.

**Tech Stack:** Git/GitHub, npm, Node.js >=20, Bun 1.3.14-compatible repository tooling, OpenCode >=1.4.0, FlowDeck/Heidi, SQLite, native FDX 0.1.0 with TypeScript fallback.

## Global Constraints

- Official stable version: `2.0.0`.
- Official Git tag: `v2.0.0`.
- Official npm package: `@heidi-dang/flowdeck@2.0.0`.
- Stable npm dist-tag: `latest`.
- Starting stable source: `main` commit `32513a722734999d814176f8d4aef66e606a9ce3` unless `origin/main` has advanced; if it has advanced, inspect every new commit before proceeding and stop if it contains unvalidated runtime changes.
- `v2.0.0-rc.1`, its npm artifact, its Git tag, and its GitHub prerelease are immutable.
- Stable runtime behavior must remain functionally identical to validated RC.1.
- No Heidi features, specialist changes, command changes, schema changes, FDX behavior changes, scheduler changes, installer redesign, or OpenCode compatibility expansion.
- Node.js compatibility remains `>=20.0.0`.
- OpenCode compatibility remains `>=1.4.0`.
- FDX compatibility remains `^0.1.0`.
- Runtime acceptance must run on the current local machine with `opencode` or `opencode serve` using `heidi / heidi-antigravity`.
- VMware, external VMs, and remote sandbox runtime acceptance are forbidden.
- Never force-push.
- Never move an existing tag.
- Never republish an existing npm version.
- Any newly discovered runtime defect stops stable promotion and requires a new prerelease such as `2.0.0-rc.2`.
- Capture and restore the user's pre-test OpenCode/FlowDeck machine state; do not expose secrets.

## File Structure

Files intentionally modified for the stable promotion:

- `package.json` — stable package version `2.0.0`.
- `package-lock.json` — top-level and root package version `2.0.0`.
- `CHANGELOG.md` — add the official `2.0.0` stable entry required by the release-alignment gate.
- `README.md` — mark v2.0.0 as stable and remove ordinary-user `@next` guidance from the active release status.
- `docs/releases/v2.0.0.md` — official stable release notes.

Files that must remain unchanged:

- `docs/releases/v2.0.0-rc.1.md` — historical RC.1 record.
- all files under `src/`.
- all files under `crates/fdx/`.
- runtime installer/Doctor behavior files.
- `.github/workflows/publish.yml` unless a previously unknown release-system defect is discovered; if that happens, stop stable promotion and return to prerelease validation rather than silently changing stable behavior.

The design/spec and this plan live on `release/v2.0.0-spec`; the actual release branch should remain a clean promotion branch from `main` and does not need to carry the planning documents unless the project explicitly chooses to merge them.
