## 1. Architecture Overview

Three-layer model:

```
IMMUTABLE SPECIFICATION (frozen at contract activation)
  contract_families  task_contracts  requirements  acceptance_criteria
  verification_rules  objectives  constraints

MUTABLE EXECUTION (per task_run, independent)
  task_runs  run_requirements  run_acceptance_criteria  assignments
  evidence  verification_results

APPEND-ONLY EVENTS (everyone reads, no one deletes)
  events  event_outbox  event_deliveries  dead_letter_events
  consumer_offsets  event_subscribers
```

**10 states**: `created → planning → analysing → delegating → executing → verifying → recovering → completed → failed → cancelled`

**5 strategies**: `simple`, `planned`, `delegated`, `audit`, `recovery`

## 3. Key Design Properties

### 3.1 Contract Immutability

- `task_contracts` stores the complete specification payload per version (no separate version table)
- After activation, `contract_lifecycle.status != 'draft'` triggers block all INSERT/UPDATE/DELETE on spec tables
- `contract_lifecycle.family_id` is kept in sync with `task_contracts.family_id` by `tr_contract_lifecycle_family_sync`
- Partial unique index `uq_contract_family_active` on `contract_lifecycle(family_id) WHERE status='active'` enforces one active version per family

### 3.2 Completion Gate (5 criteria)

All transitions to `completed` execute the identical gate:

**C1 — Assignments**: `SELECT COUNT(*) FROM assignments WHERE run_id=? AND is_required=1 AND status!='completed'` returns 0.

**C2 — SHA**: `task_runs.current_sha = task_runs.verification_sha` both non-NULL.

**C3 — Critical criteria**: `SELECT COUNT(*) FROM run_acceptance_criteria rac JOIN acceptance_criteria ac ON rac.criterion_id=ac.id WHERE rac.run_id=? AND ac.priority='critical' AND rac.status!='passed'` returns 0.

**C4 — Critical requirements**: `SELECT COUNT(*) FROM run_requirements rr JOIN requirements r ON rr.requirement_id=r.id WHERE rr.run_id=? AND r.priority='critical' AND rr.status!='verified'` returns 0.

**C5 — Required verification**: Every verification rule (`is_required=1`) must have a `current` passed result for the exact `verification_sha`. Uses `NOT EXISTS` pattern: rules with `is_required=1` must have a matching `verification_results` row with `status='passed'`, `target_sha=verification_sha`, and `is_stale=0`. Results with `pending`, `running`, `skipped`, or missing status all block completion.

**C6 — Evidence**: Every mandatory criterion must have linked evidence with `evidence.sha=verification_sha` and `evidence_lifecycle.status='current'`.

Non-overridable failures (from `override_policy`): `critical_criterion_failed`, `critical_requirement_failed`, `security_verification_failed`, `required_test_failed`, `repository_integrity_failed`, `migration_integrity_failed`, `stale_sha_detected`, `missing_mandatory_evidence`, `required_assignment_failed`. These have `is_allowed=0` in the policy table and the override insert trigger rejects them at the DB level.

### 3.3 Event Ordering

- `events.global_sequence`: PRIMARY KEY AUTOINCREMENT — ordering only, gaps are normal
- `events.event_id UNIQUE`: identity only (UUID)
- `UNIQUE(aggregate_type, aggregate_id, aggregate_version)`: version uniqueness
- Strict ordered subscriber processing: workers claim earliest pending delivery (by `event_outbox.created_ts`) where no earlier pending delivery exists for that subscriber
- Delivery ordering uses `event_outbox.created_ts`, not wall-clock timestamps, for deterministic ordering

### 3.4 Delivery

- Pre-created delivery rows: one `event_deliveries` row per matching subscriber, created during the append transaction
- Per-subscriber leasing: each delivery row has its own `claimed_by`, `claimed_at`, `lease_expiry`, `delivery_attempts`
- Two-phase delivery: Transaction A (claim lease + increment attempts, no I/O) → External deliver → Transaction B (record result, verifying lease ownership)
- Parent outbox status derivation: `delivered` when all required deliveries are `delivered`; `dead_letter` when any required delivery is `dead_letter` and none remain pending; `partially_delivered` when all required resolved but optional pending; `pending` otherwise
- Delivery attempts incremented at claim time (not after failure) to catch crash-before-failure scenarios

### 3.5 Override Policy

13 override types in `override_policy` table. 9 are non-overridable (`is_allowed=0`): critical criterion, critical requirement, security, required test, repository integrity, migration integrity, stale SHA, missing evidence, required assignment. 4 are overridable with approval requirements.

The `tr_completion_override_allowed_insert` trigger rejects overrides where:
- `override_type` has `is_allowed=0`
- approval type doesn't meet policy minimum
- target doesn't exist
- target belongs to a different run
- target already has an unconsumed override

The `tr_completion_override_allowed_update` trigger protects immutable override fields (`run_id`, `target_id`, `override_type`) and validates approval changes.

### 3.6 Command Idempotency

`command_idempotency` table with `status IN ('executing', 'completed', 'failed')`. Before executing any command, the caller inserts a row with `status='executing'`. On success, updates to `status='completed'` with the resulting `event_id` and `completion_decision_id`. On failure, updates to `status='failed'` with the error.

- Duplicate request: `idempotency_key` already exists → return existing result
- Concurrent duplicate: second insert fails on PK → caller retries, finds existing row
- Abandoned command: row has `status='executing'` for >30s → treat as failed
- Retry: clear error, set `status='executing'`, re-execute

`completion_decisions.idempotency_key TEXT NOT NULL UNIQUE` ensures completion-specific idempotency.

### 3.7 Repository Identity

`repositories` table provides stable `repository_id` FK from `worktrees`, `run_path_ownership`, `path_renames`, and `path_deletions`. Ownership scoped by `(repository_id, worktree_path, path)`.

### 3.8 Evidence

- Content immutable: `tr_evidence_immutable_update` blocks all updates; `tr_evidence_immutable_delete` blocks all deletes
- Status mutable via `evidence_lifecycle`: `current → stale → superseded → archived`
- Linked to run criteria via `run_criterion_evidence` with same-run enforcement
- Evidence is permanently preserved — archive only affects lifecycle, not traceability

## 5. Migration Strategy

Gate-driven migration (no calendar assumptions):

| Phase | Entry | Exit | Validation |
|-------|-------|------|------------|
| P1: Foundation | v0.2.6 approved | Schema creates from empty. FK check passes. All triggers/ indexes present. | `schema-v0.2.6.sql` execution |
| P2: State Machine | P1 exit | 10 states × 5 strategies correct. Invalid transitions blocked. | Transition test matrix |
| P3: Contracts | P2 exit | Triggers block mutations. Activation atomic. One active per family. | Immutability tests |
| P4: Completion | P3 exit | Gate blocks all invalid paths. Override policy enforced at DB level. | Gate test matrix |
| P5: Cleanup | P4 exit | All regression tests pass. Old Maps removed. | Full test suite |

Non-destructive rollback via feature flags, database backup before each phase, and side-by-side compatibility window for one release cycle.
